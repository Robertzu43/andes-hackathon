# Executable backend contract — Task 1

Engineering implementation, not a device/provider/AWS qualification. No live delivery or audio transcription is enabled. Automatic missed-check escalation runs only when all four check timings are configured (see [Security checks](#security-checks-part-1)). All test identities, phones and trips are synthetic.

## Run and identity

Node 24–26, PostgreSQL 15+ (tests ran PostgreSQL 18). `npm ci`, `npm run build`, `DATABASE_URL=... npm run migrate`, then configure `.env.example` through the environment and `npm start`. Migration is a separate one-off command, never API startup. `npm test` builds first and requires `TEST_DATABASE_URL` to a disposable database; each test creates/drops a unique schema.

`src/api/app.ts` exports `createApp({ctx,auth,channelSupport?})`, a Fastify instance; `await app.close()` closes all context pools. `auth` requires trusted `issuer`, `audience` and HTTPS `jwksUrl`; an injected jose `keyResolver` is available to signed-key tests. Production `src/server.ts` only reads trusted OIDC environment, supplies no synthetic resolver and supplies zero channel support by default; explicit live-send permission and complete qualification enable the configured entries. JWT signature, RS256/ES256 algorithm, issuer, audience, required subject/expiration and time validity are verified by jose. No body ID grants identity or ownership. There is no role/account bypass.

Identities map `(issuer, subject)` to a server UUID. `GET /v1/me` returns `{id}` and registers/updates the authenticated identity. A phone is eligible only from a valid E.164 `phone_number` and literal true `phone_number_verified` trusted claim. Only a verified phone claim updates the stored binding (rows are rewritten only when it changes). A token without a phone claim, or with an unverified one, never downgrades it, so it can't cancel that contact's SOS jobs. Contact acceptance checks the current authenticated claims against the frozen invitation destination; dispatch must recheck the SQL identity phone/verification and grant destination.

API JSON object schemas reject extra fields and type coercion. HTTP bodies are limited to 128 KiB. Every POST requires `Idempotency-Key` (1–128 visible ASCII characters), is transactional, and responds 200 when successful. Keys are scoped to authenticated actor, method, route and path params. Same key/content returns the persisted original response; changed JSON content returns 409. Object key order is ignored. Errors return `{code}`: validation 400, unauthorized 401, ownership/consent denial 403, missing object 404, state/idempotency conflict 409, unsupported audio 422, and redacted internal error 500. Responses use `Cache-Control: no-store`.

## SQL and worker seam

`src/db.ts` exports `createContext(databaseUrl,clock?)`, `transaction(pool,SQLCallback)`, `withTripTransaction(ctx,tripId,SQLCallback,pool?)` and `migrate(pool)`. Context owns `pool` (command capacity 6), `telemetryPool` (2) and `callbackPool` (2), each with 3s connection acquisition timeout, 5s statement/idle-transaction timeout and 30s idle timeout. Pool failures never log secrets. Telemetry authentication, upload and snapshot use telemetry capacity; command/SOS use command capacity. The clock is `() => Date`. Workers must budget extra pools across replicas rather than silently consuming API reservations.

`withTripTransaction` begins, `SELECT trips ... FOR UPDATE`, executes only SQL/state code, commits/rolls back and always releases its client. Never call network/provider/SQS while holding this transaction. Snapshot, upload, trip commands, per-trip revoke, incident read/mutation and authorization share this trip-row serialization point; no dispatch fence exists.

Standing acceptance/revoke and confirmation lock stable standing grant IDs with **`FOR NO KEY UPDATE`**, not `FOR UPDATE`. Standing revoke takes the grant row first, then every referencing trip row in native UUID order, updates standing/trip revocation and pending jobs, and commits. Confirmation locks its draft, normalizes selected UUIDs to lowercase, rejects case-alias duplicates, then takes grant locks in canonical UUID order **before inserting its new trip**. Existing-trip operations (including worker authorization) lock trip rows and read standing grants without additional explicit grant row locks. Their SQL inserts can still acquire **implicit foreign-key `KEY SHARE` locks** on standing grants; these are compatible with `NO KEY UPDATE`. Using `FOR UPDATE` for the standing grant would conflict with that implicit FK lock and deadlock against the trip-row wait. Do not change grant primary keys or upgrade grant locks in these paths. This lock compatibility plus stable ordering serializes revoke with existing-trip authorization and concurrent new-trip insertion. Authorization-first may finish later; revoke-first must deny. Worker authorization must recheck both `contact_grants.revoked_at` and `trip_grants.revoked_at`, accepted scope, subject/destination verification and current trip/incident state in its trip transaction.

Migration `001-core.sql` is immutable once applied; `schema_migrations(version,hash)` plus a migration-only advisory lock make repetition/concurrent invocation safe and changed applied SQL fail closed. Task 2 may add numbered migrations and extend the runner. SQL tables:

- `identities`, owned `trucks`, `trip_drafts`, `trips` (version, map/checkin states), standing `contact_grants`, selected `trip_grants` (revocation attribution).
- `locations`, `latest_locations`; latest changes only for newer capture time.
- `incidents`, partial unique active incident per trip; `trip_events`, `incident_events` distinguish SOS report, receipt/action and driver resolution.
- `idempotency(actor_id,scope,key,request_hash,response,created_at)` with unique actor/scope/key, canonical content hash and short transaction-scoped per-key advisory lock. Advisory locks are never held for dispatch/network.
- `jobs(id,trip_id,incident_id,grant_id,recipient_id,channel,class,version,status,unavailable_reason,created_at,due_at,expires_at,cancelled_at)`. `channel`: sms/whatsapp/voice/group. `class`: emergency/ordinary. Status allows pending, claimed, authorized, accepted, rejected, unknown, delivered, cancelled, unavailable. Incident/recipient/channel has a partial unique index with nulls not distinct (one group fact, distinct individual channels); ordinary jobs with no incident are not constrained by that incident index. Task 2 adds lease/attempt/quota details. Statuses represent facts, never inferred delivery.
- `outbox(id,job_id,job_version,class,created_at,published_at,lease_owner,lease_until,next_publish_at)`, unique job/version, due index. Initial eligible SOS jobs/outbox are inserted atomically. Queue payload may contain only IDs/version/class, never phone, raw text or coordinates. Version mismatch/cancelled SQL job must prevent new authorization even if an old outbox message publishes.
- Migration `004-insights.sql` adds incident location snapshot columns (filled by a BEFORE INSERT trigger from `latest_locations`), incident `label/labeled_at/labeled_by`, the `reports` table, the `security_events` view (robo/intento_robo labelled incidents with a location plus reports) and `time_band(timestamptz,text)`. Migration `005-insights-hardening.sql` adds a reporter/time index for the report rate limit and excludes incidents whose copied location is more than an hour older than the alert.

SOS snapshots accepted unrevoked incident recipients, deduplicated by standing driver/contact uniqueness, and creates separate SMS/WhatsApp/voice jobs immediately. Missing country/channel/locale support or mismatched current verified phone creates explicit unavailable jobs with reasons and **no outbox**. A separate group job is always unavailable with `group_support_unverified`; individuals never substitute for group delivery. Test factory options supply explicit synthetic support. Production support is empty by default; Task 2 below adds the optional configured adapter and requires explicit live-send permission for new jobs.

Close, resolve and either revoke cancel only pending/claimed affected jobs (incrementing job version); authorized/unknown/in-flight facts remain. Stale transport must be rechecked against SQL. Trip closure never automatically resolves SOS, and SOS after closure must never gain fresh map coordinates. Contact incident read/ack/action needs incident consent but does not require active map, so an open security episode can continue after arrival without fresh coordinates. Fields in `src/contracts.ts` export Actor, Trip, Job, Outbox and Channel/ChannelSupport for the next runtime slice.

## Task 2 — executable durable dispatch

`npm run build` then `npm run migrate` applies ordered, hash-checked numbered SQL migrations, including `002-dispatch`; `001-core.sql` remains unchanged. API `npm start`, control `npm run worker:control`, emergency `npm run worker:emergency`, ordinary `npm run worker:ordinary` are separate processes/services built from the same image. No migration runs on startup. Workers require `DATABASE_URL`, `AWS_REGION`, `SQS_EMERGENCY_URL`, `SQS_ORDINARY_URL`; use task-role AWS credentials and HTTPS Standard queues, with separate DLQs. SQS permissions: control `sqs:SendMessage`; each consumer `sqs:ReceiveMessage`, `sqs:DeleteMessage`, `sqs:ChangeMessageVisibility` on its class queue. No blind DLQ redrive grants sending authority.

The API reserves at most **10 connections per replica**: commands 6, telemetry 2, callbacks 2. Each worker uses at most **2 command connections**; its unused lazy telemetry/callback pools open no connections. Budget RDS connections as `10*API replicas + 2*(control+emergency+ordinary replicas) + migration/operations headroom`; replicas and database capacity must be explicitly capped by infrastructure. The initial delivery role has two slots independently for each of SMS, WhatsApp and voice (six external calls maximum per replica), across all receive batches. SQL decides the channel before a slot is assigned. Saturated messages get 30-second SQS visibility deferral, leaving the receive pump free for other channels. No SQL client/transaction is held during SQS or provider I/O. Control relay, scanner and each channel's read reconciliation run independently. SIGINT/SIGTERM abort long polls and stop new claims and authorizations. An already authorized send is never aborted: it finishes within the provider's 10-second timeout (inside the ECS StopTimeout), so its message ID is kept. A claim left unauthorized expires and is reclaimed. Provider fetch has a 10-second client timeout with no HTTP retries or redirects; this is an engineering resource bound, not a safety deadline or server cancellation guarantee.

`src/notifications/dispatch.ts` exports `relayOnce`, `recoverWork`, `claimJob`, `authorizeJob`, `runJob`, `finishAttempt`, `reconcileOnce`, `saveCallback`, `consume`; `src/worker.ts` exports `control` and `startWorker`. `src/notifications/sqs.ts` is the actual AWS SDK v3 adapter. Queue JSON has exactly `{jobId,version,class}`, no channel, phone, text or location. Runtime uses real AWS transport only; there is no synthetic startup fallback. SDK transport retries can duplicate queue publications, never provider attempts.

The SQL lease is 30 seconds. Relay updates use unique ownership tokens; an old publisher cannot acknowledge a newer lease. Lost publish acknowledgements republish only transport, with persisted exponential backoff up to five minutes. Scanner runs every second and restores pending jobs/outbox after lost/expired transport no sooner than 60 seconds after a confirmed publication. Claimed work without an external attempt can be reclaimed after expiry, and its outbox is republished in that same recovery pass (its message was already consumed); stale tokens cannot authorize. Claiming and authorization read the clock after their lock waits, and terminal job expiry is checked before the lease, so expired work ends `cancelled`. Authorization re-reads the contact's verified phone after the account-lock wait. A unique `dispatch_attempts(job_id, job_version)` permits one external attempt per job version. SQL authorization rechecks current standing/trip consent, incident scope, matching verified destination, incident owner/state, class, version, due time, expiry and qualification while holding the existing trip-row lock. Standing grants are read without upgrading the `NO KEY UPDATE` lock graph. A crash after authorization yields unknown, never pending. Queue replay and scanner cannot create another external attempt, even after HTTP 404 reconciliation or a rejection. Ambiguous results are **never resent**. Only a definitive retryable rejection (HTTP 429/401/402/403, meaning nothing was sent) returns the job to `pending` at a new version, with persisted backoff (30 s, 60 s, 120 s) and a budget of 3 (`jobs.retry_count`, migration `006`). Every retry is a fresh attempt authorized under the trip lock, so resolution, revocation or expiry in between stops it. Permanent rejections (400/404) are terminal and need operator review. A genuinely new driver-declared episode requires explicit resolution and a new SOS; retries must not be used to resend an ambiguous prior episode.

Every authorized attempt freezes the provider payload, its SHA-256 hash, destination hash, owner/token and stable provider key before network. The alert summary (`src/notifications/wording.ts`, Spanish only for the demo) names the truck label, says what triggered it (SOS, or the missed-check reason) and carries the exact incident UUID (`Incidente <id>.`). SMS, WhatsApp and voice all carry that UUID in the frozen summary so the authenticated recipient can read, acknowledge and report actions for the same episode; the ID grants no access by itself and is not a bearer link. It includes the persisted capture time (HH:MM in the trip time zone), the location age, rounded accuracy and a Google Maps link to the last latitude/longitude only when map access and standing/trip map consent remain valid at authorization. The existing 120-second freshness bound is synthetic. Otherwise it truthfully says `Última ubicación no disponible`. Arrival keeps SOS active while preventing newly authorized payloads from gaining coordinates. Payloads already authorized may finish after revoke/closure. Untrusted raw trip text is never copied. The driver's truck label is, collapsed to one line and at most 40 characters. Voice summaries omit URLs and read capture time, age and accuracy instead. WhatsApp places the entire summary in one explicitly configured approved-template variable; text and voice append it to qualified configured text. Incident acknowledgements/actions remain separate from provider acceptance/delivery.

### Provider configuration and evidence

The default `ZAVU_LIVE_SEND=false` gives API zero supported channels, denies new authorization and refuses delivery-role startup. With retained complete credentials/qualification, control still performs read-only GET reconciliation of existing known message IDs and authenticated callbacks remain enabled. Missing configuration leaves provider access disabled. The send method independently rejects POST while the flag is false. To enable actual sending, set the literal `ZAVU_LIVE_SEND=true`, inject server-only `ZAVU_API_KEY`, `ZAVU_PROJECT_ID`, `ZAVU_SENDER_ID`, `ZAVU_CALLBACK_SECRET`, and `ZAVU_QUALIFICATION_JSON`. The JSON must contain:

- `accountId` equal to `ZAVU_PROJECT_ID`, `senderId` equal to `ZAVU_SENDER_ID`, nonempty `evidence` referencing actual account/balance/limit qualification.
- Positive integer `dailyLimit`, `channelDailyLimit`, `minuteLimit`; nonnegative integer `emergencyReserve` smaller than all three. These are explicitly qualified conservative account budgets, not public Zavu defaults. They must cover account traffic from all applications, not just this service.
- `entries`: unique `{channel,country,locale,evidence,text}` objects. Country is an explicit two-letter uppercase code, locale a canonical Intl locale, evidence references sender/destination/channel qualification, and text is approved localized safety copy. Voice additionally needs `voiceLanguage` exactly `es-ES` or `pt-BR`; WhatsApp additionally needs account-approved `templateId` and `summaryVariable` (one documented positional or named string key). Template qualification must allow the full timestamp/location summary. No group entry is supported. A nonempty evidence reference is a configuration assertion, not independently verified by code; operators must verify its contents before enablement. Test-only fixtures explicitly use `syntheticfixture:` evidence and are rejected by production environment loading.

`quota_reservations` persists send reservations per account/channel/day. `provider_requests` persists all send/read request reservations for a sliding minute, including across UTC midnight. Account-row locks serialize replicas. Ordinary sends and background reconciliation leave the configured emergency margin; emergency sends can use it. Reservations are conservative and retained after refusal/timeout. Actual rate enforcement occurs at authorization/read reservation time; delayed already authorized emitters and external account users can still encounter provider throttles. Refusals are recorded without automatically sending again. Quota denial returns an unattempted job to SQL pending, due in one minute; scanner restores transport. There are no validated price/cost assumptions: these count limits bound usage, not a currency billing guarantee.

After acquiring the contended account-row lock, authorization refreshes its clock
and rechecks both the claim lease and job expiry before creating an attempt or
reserving send quota. Equality is expired. Authorization, reservation windows and
reservation timestamps use this refreshed time. A lease that expires during the
wait grants no new authority; an expired job is cancelled without an attempt.

`POST /v1/callbacks/zavu` is registered only with complete callback context. It uses a separate two-connection pool and exact raw `application/json` bytes. No OIDC token or API idempotency key is required; strict v2 HMAC authentication uses the configured project/sender/secret, exact `t + '.' + bytes`, constant-time comparison and documented -300/+60-second window. Durable `(project,eventId)` dedupe and evidence commit precede 200; storage failure returns 500. No raw payload, signature, phone, coordinates, freeform provider error text or credential is logged/stored as callback evidence: only exact-byte SHA-256 hash, selected verified IDs/status/type, hashed destination, safe error code and timing. Minimal event evidence expires after seven days and scanner deletes it; dedupe consequently has that same retention. Sensitive attempt payload expires after 24 hours and scanner clears it, preserving hashes/facts for unresolved attempts; quota windows prune after two days. These are explicit synthetic engineering retention bounds, not legal/data-policy qualification. Core API/audit/location retention still needs the separate policy noted above.

Callbacks arriving before HTTP response remain unmatched by exact message ID. Only a subsequently persisted response ID can map them; phone/time/text never correlate attempts. Timeout without ID remains unresolved, even if a matching-phone event exists. Reconciliation only GETs the known official message ID; it never POSTs or lists by guessed correlation. ID/channel/destination must match read evidence. Delivered/read facts do not regress under late queued, failed, unknown or HTTP timeout results. Voice receipts remain evidence without claiming human answer/playback semantics; existing-group sends remain unavailable. Source-unspecified key TTL, cancellation and read-only key lookup remain unsupported. See [Zavu research](zavu-research.md) for exact source contracts and qualification gaps. No test key is safe for network tests.

With it unset, complete raw `PGHOST`, `PGDATABASE`, `PGUSER`, `PGPASSWORD` and optional `PGPORT` form an in-memory URL with encoded credential components. Runtime tasks receive only the app credential. Migration does not run on service startup. `/health` still checks SELECT 1; operators must confirm the bootstrap container exit code 0 before enabling any service. ## Security checks (Part 1)

Spec: [security checks and incident data design](../superpowers/specs/2026-10-17-security-checks-incident-data-design.md). The control worker runs `checkOnce` (`src/checks/sweep.ts`) every `CHECK_SWEEP_MS` only when `SILENCE_MS`, `ASK_GRACE_MS`, `ARRIVAL_GRACE_MS` and `CHECK_SWEEP_MS` are all set. Setting only some of them fails startup. Demo values are 120000/60000/120000/5000 so a check fires on stage. They are not evidence-backed safety thresholds (#11 limits stay unset), and the production `infra/template.json` deliberately leaves them unset.

A sign of life is the latest of: location receipt (`latest_locations.received_at`, which only moves when a newer capture time arrives, so a heartbeat must carry a new `capturedAt`), a driver `checkin_ok` or `resume` command, an incident resolution, or trip creation. An active, unpaused trip with check-ins on, no active incident and no open check opens one `security_checks` row (`asking`, `ask_until = now + ASK_GRACE_MS`) for the first matching reason:

1. `sharing_stopped`: `sharing_stopped_at` is later than the last sign of life.
2. `silence`: no sign of life for `SILENCE_MS`.
3. `arrival_overdue`: the later of `expected_arrival_at` and the driver's last action (trip start, OK, resume or incident resolution) passed more than `ARRIVAL_GRACE_MS` ago.

Closing an open check:
- `checkin_ok` → `ok`.
- `arrived`, `cancel` or `pause` → `cancelled`.
- SOS → `escalated`, linked to the SOS incident.
- At `ask_until`, the sweeper escalates. It attaches to an already active incident, or creates one with `trigger='missed_check'` and `check_reason`, plus the same fan-out as SOS.
- A sharing resume cancels an open `sharing_stopped` check.

Each trip is handled in its own short SQL-only trip transaction, so one failing trip does not block others and a restart neither loses nor duplicates an escalation.

An explicit SOS always reaches the recipients with SOS wording. An SOS during an active missed-check incident keeps the same incident, sets `trigger='sos'`, clears `check_reason`, cancels its unsent (`pending`/`claimed`) missed-check jobs as `superseded_by_sos`, and fans out a new SOS wave. Jobs carry their `trigger`, and the unique key is (incident, recipient, channel, trigger), so repeated or concurrent SOS taps add nothing more. Attempted missed-check work keeps its facts and is never resent. Status `deliveries` lists the current wave only.

A late `checkin_ok` after escalation is recorded but changes nothing else: the incident stays active and its alerts stay pending. Only an explicit `POST /v1/incidents/:id/resolve` cancels them, and an OK never cancels SOS work. Once escalated, contacts may already be alerted, and an OK given under duress must not silence the rest.

Fan-out (`createIncident`, shared by SOS and escalation): accepted incident-scope `family` contacts get SMS, WhatsApp and voice jobs; `colleague` contacts get SMS and WhatsApp; the group job stays `unavailable` / `group_support_unverified`. `POST /v1/contacts` accepts an optional `role` (`family` default, or `colleague`). Drafts accept an optional `expectedArrivalAt`: any RFC 3339 date-time (case-insensitive `T`/`Z`, offsets, a leap second rolls over), with no range limit. Draft `fields` echo it as sent; confirmation stores the instant, and status returns it normalized to ISO UTC. A past instant means "already due": overdue still waits `ARRIVAL_GRACE_MS` from the trip start.

| Route | Body / behavior |
|---|---|
| `POST /v1/trips/:id/sharing` | Owner only, idempotent. `{state:'stopped'\|'resumed', reason:'user'\|'page_hidden'\|'permission_denied'\|'error'}`. `stopped` records its own time in `sharing_stopped_at`, so a stop after an OK opens a new check; `resumed` clears it and cancels an open `sharing_stopped` check (other open checks stay). Each call appends a `trip_events` row (`sharing_stopped:<reason>` or `sharing_resumed`). Closed trip → 409. Returns `{id,sharing}`. |
| `GET /v1/trips/:id/status` | Driver or a contact with an accepted, unrevoked grant on the trip. Returns `{trip:{status,paused,expectedArrivalAt}, check:{status:'asking',reason,askUntil}\|null, incident:{id,trigger,checkReason,status,label,createdAt}\|null, deliveries:[{role,channel,status,unavailableReason}], location?:{freshness,ageMs,capturedAt,accuracy}}`. `incident` is the latest incident (active or resolved); it, `check` and `deliveries` are shown only to the driver or incident-scope contacts (map-only contacts get `check:null`). `location` appears only for the driver or map-scope contacts while the map is active. No phone numbers or recipient IDs. It is one read-only repeatable-read snapshot on command capacity with no trip lock, so polls never wait behind writers or use telemetry capacity. |

Alert-text settings for the delivery workers: `EMERGENCY_NUMBERS` (JSON by trip country, e.g. `{"PE":"105","BR":"190"}`; missing → the sentence is omitted) and `CONTACT_APP_URL` (adds `Ver: <url>/incidents/<id>`). Zavu prefixes SMS/voice with the qualification `text`, so set it to `ANDES:`.

## Demo mode

For the judges' demo only. `DEMO_MODE=true` replaces OIDC with an in-process RS256 demo issuer (`src/demo.ts`). Real identity tokens are rejected, and every other route keeps the same JWT, ownership and consent checks. Live sends are refused by default. They are possible only through three gates, each failing closed:
1. `DEMO_LIVE_PHONE` names the one consented E.164 number (the demo issuer refuses to start otherwise). Only the family persona uses it; the driver and colleague keep fictional numbers.
2. The Zavu qualification sets `allowedDestinations` to exactly `[DEMO_LIVE_PHONE]` and a `demoLimits` budget `{perIncident, perSession}` (positive integers; the API and workers refuse to start otherwise).
3. `authorizeJob`, before quota or any provider call, marks any other destination `unavailable` / `destination_not_allowed`, and any job past the budget `unavailable` / `demo_budget_exhausted`. `perIncident` counts attempts on the incident; `perSession` counts attempts to the recipient identity, which is the world's one consented persona. Both are counted under the account lock. The global budget is the qualification's existing `dailyLimit` / `channelDailyLimit` / `minuteLimit`.

So the fictional numbers and other people can never be contacted. Personas can invite only personas of their own world (403 `demo_world_boundary`), so worlds cannot pool the consented phone onto one trip. The budget is operator policy, not a code default; a single family persona needs 3 attempts per alert wave (6 if a missed-check alert is followed by an SOS). Never enable demo mode on a deployment with real users.

`POST /v1/demo/session` with `{}` is unauthenticated and needs no Idempotency-Key (a deliberate exception: there is no actor yet). Each call creates an isolated synthetic world:
- a driver, a `family` contact and a `colleague` contact, with fictional `+1555555010x` numbers;
- a truck labelled `ABC-123 (demo)`;
- accepted map+incident grants.

It returns `{synthetic:true, expiresInSeconds:7200, driver:{id,token,truckId}, family:{id,token,grantId}, colleague:{id,token,grantId}}`. Keep the tokens in memory and switch personas client-side.

Limits:
- At most 30 worlds per minute per instance (429 `demo_rate_limited`).
- The signing key lives in memory, so tokens end on restart and the demo must run a single instance.
- Demo rows stay in the database until it is dropped after the event.
- Abandoned worlds alert nobody. With `DEMO_MODE=true`, the control worker opens a check only if the trip's driver or a current contact made an authenticated request (a `/status` poll counts) within the last `ASK_GRACE_MS`, and escalates it only if one did after it opened; otherwise the open check is cancelled at its deadline. A closed tab, or tokens that died with a restart, therefore stop all automatic checks. Keep `/status` polling while a demo screen is open. An explicit SOS is never affected.

## Incident data and insights

- **Settings.** `INSIGHTS_TIME_ZONE` (default `America/Lima`; IANA names only, because PostgreSQL reads offsets such as `-05:00` with the opposite sign), `INSIGHTS_MIN_COUNT` (default 3, never below 3), `DEMO_MODE=true` (insights follows `createApp`'s demo issuer, so it is on only when demo-persona sign-in is; demo personas are stored as synthetic identities and their reports as synthetic rows, because personas are free to create; that provenance is kept with the data, so demo reports and incidents stay demo data after a restart without demo sign-in, and real data stays real after a restart with it), and `SEED_DEMO=1 npm run seed:demo` for synthetic demo data. `npm run build` must run before seeding, because the script imports `dist/`; it is included in the image. On AWS the database is private, so seeding needs a separately authorised one-off task, which is not configured. Remove demo data with `DELETE FROM reports WHERE synthetic`.
- **Known pre-production limits, accepted by Robert for the hackathon demo (recorded on PR #76):**
  1. **Colluding verified accounts.**
     - *Risk:* three phone-verified accounts acting together can publish a cell that contains one other person's report. That reveals that someone reported a robbery or attempt in that ~5 km cell and day/night band within the last 90 days. Cost to an attacker: three real verified numbers.
     - *Fix path before real data:* raise the distinct-contributor minimum (e.g. 5 or more), weight contributors by account age or reputation, or add calibrated noise to published counts (differential privacy), with a methodology and privacy review.
  2. **Hour-attributable changes.**
     - *Risk:* the public view is recomputed once per hour, so a change to a published cell (a new report, a label or a relabel) can be tied to the hour in which it surfaced.
     - *Fix path:* publish on a daily cadence (a staler map), delay publication by a random interval, or add noise to counts as above.
- **Location.** Incidents copy the trip's latest location when they are created; an incident counts only if that location is at most an hour older than the alert. `falsa_alarma`, `sin_senal` and `otro` labels never reach hotspots or advice. Incident snapshots and report coordinates are kept with no deletion scheduler, so they fall under the same unqualified-deletion caveat as other location data before live collection.

## Known backend limits (accepted for the demo)

A review of the backend at `c752de8` found 15 issues. Robert chose to fix the 5 critical ones in the reconciliation PR:
- shutdown aborting authorized sends;
- unparseable capture times bypassing the bounds;
- non-canonical locales disabling every channel;
- phone-claim downgrades cancelling SOS jobs;
- terminal handling of 429/401/402/403.

The reviews of this PR led to further fixes, each with a regression test (`tests/hardening.test.mjs`, `tests/dispatch-races.test.mjs`):
- trips stored with a non-canonical locale before the fix (`pt-br`) are matched canonically;
- a job whose lifetime and claim both lapse during the quota wait ends `cancelled`;
- the contact's verified phone is re-read after the quota wait;
- claims read the clock after the trip lock, and a lapsed claim's outbox is republished at once.

He accepted the other 10 as documented production limits for the hackathon. Limit 3 has since been fixed; the other nine stand:

1. **Endless reconciliation** (`dispatch.ts` reconcile). Accepted voice, SMS/WhatsApp ending `failed` or never `delivered`/`read`, and no-ID `unknown` attempts keep being re-queued for reconciliation.
2. **Lost result after an SQL failure.** `finishAttempt` runs once, with no retry. A transient SQL failure after the provider call can leave an accepted send recorded as `authorized`/`unknown`.
3. **Uppercase self-invite. Fixed.** The guard compared the UUID case-sensitively, so an uppercase self ID passed it and hit the database CHECK: a 500 whose PostgreSQL detail (the failing row, phone included) could reach RDS/CloudWatch logs. It now compares case-insensitively and returns 400 `invalid_consent_request`.
4. **Read paths take the trip row lock.** `withTripTransaction` takes `FOR UPDATE` for read-only snapshot, trip and incident reads too, and location ingest holds it while writing samples. (`GET /v1/trips/:id/status` no longer does: it is a lock-free snapshot on command capacity.)
5. **Recovery scans.** `recoverWork` runs nine mostly unindexed statements in one transaction every second on each control replica.
6. **Deferral can exhaust receives.** `consume` defers messages it can't fit in a slot, and each deferral counts toward SQS `maxReceiveCount` (5), so busy channels can push valid work to the DLQ. SQL recovery restores it.
7. **Unguarded receive loop.** In `consume`, the job lookup, `ack` and `defer` calls have no try/catch, so one transient DB or SQS error ends that receive iteration.
8. **Idempotency rows are never deleted.** Every idempotent mutation, including each telemetry POST, keeps its stored response.
9. **Slow, unordered relay.** The relay publishes one outbox row per 100 ms per control task, with no emergency-first ordering, and `publish_attempts` is never reset.
10. **Unsalted destination hash.** `destination_hash` is an unsalted SHA-256 of the E.164 number and is kept indefinitely in attempts and callback evidence.

Apart from limit 3, none of these is fixed or claimed fixed. Each needs its own change and test before production use.
